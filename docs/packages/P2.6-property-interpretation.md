# P2.6 — property-aware interpretation and semantic evaluator

Package: property interpretation v1 plus executable evaluation foundation
Objective: expose exact user intent and judge semantic outcomes rather than
schema-pass percentages
Dependencies: IR/intent/protocol v1, semantic import (`b72fabe`)
Allowed paths: interpretation/eval/backdrop modules, intent constraints, provider
and CLI integration, opt-in Neovim v1 path, fixtures/tests and compatibility docs
Contract version: interpretation 1, prompt `property-intent-1`, intent/protocol 1

## Delivered

- `interpret --v1` produces a strict property-aware interpretation. Required
  nullable fields are explicit, unknown keys rejected, numbers validated by
  the deterministic engine, and actual-theme targets checked.
- Decisions: ready, unchanged, needs_clarification, unsupported. Clarification
  has questions and no actions; unsupported names the limitation. No spec is
  written for either, even when an existing output path was supplied.
- Property exactness: lock bg separately from opacity, request/persistent scope,
  explicit unlock, typography bool/reset/clear, optional semantic override
  targets. The preflight returns real refusal/infeasibility/no-op reports.
- Trusted anchors: set_color accepts opaque #rgb/#rrggbb colors explicitly
  present in the current request. Inventory/model/prior text does not grant
  new anchor authority. Translucent literal anchors remain unsupported; separate
  explicit opacity edits are supported.
- Dynamic contrast backdrops: existing literal colors remain compatible; role
  scenes resolve against the candidate and are rechecked at the end, including
  persistent requirements on subsequent requests. Overlays that replace fg or
  require unknown external blending are unverified/fail closed.
- Semantic required-floor checks enumerate bounded applicable modifier/language
  combinations, so separately passing color and opacity rules cannot hide an
  unreadable combination. More than 256 contexts or 8 modifiers is unverified;
  no broad optimality/conformance claim is made.
- `eval-interpretation` checks required/forbidden semantic outcomes: property
  preservation, only-allowed changes, values, locks, states, strength ranges,
  contrast and decisions. SHA-256 hashes record suite/run/input/response/prompt;
  failures are categorized separately from schema validity.
- Twelve executable cases are linked to the 50-request corpus; four are held-out.
  The checked-in run is explicitly hand-authored canned replay, not a provider
  benchmark. A schema-valid unrelated edit has a negative regression test.
- `:HexwitchV1` and `refine(...,{v1=true})` use protocol responses, retain property
  reports, show clarification, and refuse rolled-back candidates. Legacy replay
  stays unchanged. Iteration context can be supplied as a reviewed file.

## Usage

```sh
hexwitch --machine interpret core/eval/themes/nord.json \
  'Keep the background color, but remove its transparency.' \
  --v1 --from-llm core/eval/llm/property-opaque-background.json --out intent.json

hexwitch --machine revise core/eval/themes/nord.json --spec intent.json

hexwitch --machine eval-interpretation core/eval/interpretation-suite-v1.json \
  --run core/eval/interpretation-contract-replay.json
```

Live calls require an explicit `--provider`, are not part of CI, and use the v1
structured-output schema. `--dry-run --v1` reveals exact prompts without network.
A context file contains previous_requests and previous_actions; it is treated as
data. The model's relative interpretation is still evaluated, not presumed correct.

## Compatibility

- Interpretation v1 is opt-in. Legacy `LlmSpec`/EditSpec remain supported.
- CLI v1 stdout is an interpretation/report, not a raw EditSpec. `--out` writes
  only the reviewed IntentSpec when an actionable response exists.
- Background arrays now accept literal hex OR `{surface,overlays}`. Older engines
  reject the additive shape. Discover `intent_features.role_backdrops` first.
- Intent reports add `rolled_back`, semantic_context. Proposed moves in a rolled
  back report are not retained; clients must inspect the flag before applying.
- Unsupported interpretation maps to refused protocol outcome plus explicit
  decision=unsupported. Transport/parser errors stay stable protocol errors.
- Unlock authorization is semantic; no keyword heuristic pretends to prove user
  intent. The exact unlock operation stays reviewable and must be evaluated.

## Acceptance evidence and limits

Verification: 138 Rust tests and 4 Python metadata/corpus tests pass; formatting
and clippy pass. The canned executable suite passes 12/12 (8 development / 4
held-out); this is not a live-model accuracy result.

Focused tests cover positive edits, absent properties, unknown/irrelevant/missing
fields, trusted anchors, negative selectors, provider refusal/truncation, required
rollback, sequential persistent constraints, semantic combinations, clarification
without file overwrite, actual headless-Neovim replay and schema-valid unintended
changes. Full verification is recorded in docs/IMPLEMENTATION_STATUS.md.

Still pending: live model/prompt comparison, annotations for every corpus case,
independently reviewed labels, full repeated-iteration/session-context quality,
relational prominence/identity operations, image/reference anchor selection,
provider cancellation/structured-output fallback and wider editor conformance.
Reproducibility hashes do not prove a record truly came from a claimed provider.
No phase-2 quality gate or subjective aesthetic result is declared complete.
