# P2.6 — semantic evaluation matrix

Package: complete annotated-request execution, state variants, sequences,
paired consistency and evaluator sensitivity tests
Dependencies: property-aware bridge/evaluator (`abca8f7`)
Contract version: evaluation suite/run 1 with optional additive case/pair fields
Objective: measure intent preservation and failure classes without treating JSON
validity, clarification counts or canned replay as model accuracy

## Deliverables

- `interpretation-matrix-v1.json`: 74 authored cases, covering all 50 request IDs,
  15 state/context variants, one paraphrase case and eight sequence turns.
- `states/`: authored light/dark references plus a dark reference with an unrelated
  extension role. Styles expose typography and semantic overrides deliberately.
- Three paired checks: paraphrase equivalence, slightly-versus-much strength, and
  invariance when an unrelated role is added.
- `interpretation-matrix-replay.json`: labeled offline, hand-authored contract
  responses. It is not model output and must not be presented as a benchmark.
- Thirteen known-bad replay perturbations in `mutations/`, with expected detectors:
  wrong targets, excess lock/unlock, unrelated recoloring, missing semantic italics,
  needless clarification, untrusted color, reversed strength, sequential protection,
  omitted selection context, omitted persistent floor and unrelated decoration clear.
- Annotation validation independent of responses; malformed gold contracts are
  authoring errors. Bounded nested alternatives do not combine incompatible answers.
- Sequential evaluation uses the actual prior candidate/result. Missing/unparseable
  responses block dependent turns rather than silently loading fresh references.
  Semantically wrong but executable prior turns continue with their actual state,
  and downstream results flag upstream_failed. Refused/rolled-back proposed actions
  are not recorded as executed context.
- Scorecards distinguish property correctness, preservation, forbidden operations,
  unrelated changes, readability, hierarchy proxies, strength and identity proxies.
  Missing response/dependency checks count as not_evaluated rather than disappearing.
  Edit, clarification, unsupported, refusal and mixed buckets are reported separately.
- Pair-only failures affect the top-level evaluation outcome and normal CLI exit.
- Python tests ensure corpus IDs/request/split/category are retained and all authored
  generated fixtures rebuild byte-identically. Offline Rust tests assert every known
  mutation triggers its intended detector, not merely any generic parse failure.

## Why evaluate proposals as well as final state?

A model can propose an unsolicited unlock, then have a later required constraint
roll the candidate back. Final-state preservation alone would hide the unsafe
interpretation. `action_absent` checks catch this even if the engine prevented harm.
Similarly, readable starting text does not prove a persistent or multi-background
floor was understood: `contrast_requested` checks contexts and lifetime explicitly.

## Verification

143 Rust tests and seven Python metadata/corpus/rebuild tests pass. The authored
matrix passes 74/74 and 3/3 pairs; all 13 known-bad sensitivity probes trigger
their intended detectors. Formatting/clippy pass. These counts establish the
evaluator's regression behavior, not a model's accuracy.

## Run locally

```sh
hexwitch --machine eval-interpretation core/eval/interpretation-matrix-v1.json \
  --run core/eval/interpretation-matrix-replay.json --out evaluation.json

cargo test --manifest-path core/Cargo.toml --all --locked
python3 -m unittest discover -s core/eval -p 'test_*.py'
```

Rebuild authored artifacts with `build-eval-matrix.py` then `build-eval-mutations.py`.
The builders never call the engine or derive expected values from its output.
The original 12-case suite/replay remains unchanged for compatibility.

## Reading the scorecard

- Case pass: all required predicates or a complete accepted alternative pass.
- Schema/validation failures: separate failure_class, plus not_evaluated predicate
  counts. They are not counted as passing preservation simply because no edit ran.
- Pair pass: both cases executed and passed, start states are compatible, and the
  declared relation holds. No random minor perturbation score is substituted.
- Strength/readability/secondary: deterministic numerical checks, not aesthetics,
  comfort, productivity or proof of rendered-editor conformance.
- Expectation buckets: clarification on an actionable edit is not editing success;
  correct refusal is tracked separately. Do not publish just one aggregate number.

## Compatibility

Optional fields: Case.setup, previous, source_id, expectation; Suite.pairs.
Existing v1 suites default to edit expectation and isolated cases. Reports add
checks with evaluated flags, upstream_failed, pairs/pair_failures, scorecard and
results_by_expectation. Consumers must inspect pair_failures as well as failed.
Older evaluators reject the new schema rather than silently discard it.

## Limitations and next evidence gate

All cases inspected during implementation are development/regression material.
Original held_out labels are retained for traceability, but are NOT a fresh
independent holdout. Independent annotation and new unseen cases are still needed.
The all-50 coverage means executable checks exist, not that every subjective
acceptable interpretation is captured. Some requests with unavailable context or
unsupported relations are explicitly clarification cases; expand those only with
reviewed new acceptable branches, not by changing golds to current model outputs.

No live provider requests or human preference evaluation were run. Next: collect
recorded outputs with explicit provider approval, exact prompts/revisions and
configuration; report repeated-run variance and categorized failures. Then add
real-editor scene evidence and blinded human review separately. No phase-2
trustworthy-adaptation gate is claimed complete based on canned replay alone.
